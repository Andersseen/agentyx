# 0.8 — Install explicit project context

Prerequisite: R070-04. Read [the playbook](session-playbook.md).

## Chosen design

Add an optional `context` field to `.agentyx.json`. Keep three kinds of project facts:
commands, directory responsibilities, and constraints. Commands are instruction data;
Agentyx never executes them.

```json
{
  "packs": ["technical", "typescript"],
  "targets": ["codex", "claude"],
  "context": {
    "commands": {
      "verify": { "command": "pnpm check", "cwd": "." },
      "testCore": { "command": "pnpm vitest run packages/core", "cwd": "." }
    },
    "areas": [
      { "path": "packages/core", "purpose": "Provider-neutral domain logic." }
    ],
    "constraints": [
      "Keep terminal output outside packages/core.",
      "Do not edit generated schema files by hand."
    ]
  }
}
```

Use portable project-relative paths, including `.` where meaningful; reject absolute paths,
parent traversal, backslashes, and symlink escapes using existing containment patterns. Validate
command working directories and area paths against the project during project loading. A missing
declared path is an explicit error, not a guessed replacement. Commands must be non-empty strings;
do not shell-parse them, expand variables, resolve secrets, or claim they are executable.

An absent context preserves current behavior. Empty context produces no extra skill. Non-empty
context contributes exactly one generated, provider-neutral skill named `agentyx-project-context`.
Reserve this name; a local or built-in collision is a domain error. It is a project contribution,
not an entry added to every pack. Exclude it by omitting context; do not add a second enable flag
or allow pack exclusions to silently discard it.

Store its reusable instructions as a packaged Markdown asset, for example
`packages/core/templates/project-context.md`. Serialize the validated project facts deterministically
as data and combine them with that asset through `formatSkillMarkdown`. Do not put a reusable skill
body in a TypeScript constant. Add the template directory to package assets and keep `src/assets.ts`
at its current depth.

Install this skill through the existing adapter/planner/executor path. No new provider-specific
instruction writer, no edits to `AGENTS.md`, no changes to the user's global agent configuration.
Its instructions describe the facts as repository guidance that does not override user requests or
higher-priority instructions. Installation cannot guarantee the provider activates the skill.

## R080-01 — Model and validate project facts

Prerequisite: R070-04. Start with core config schema/project loader/errors and project tests.

Steps:

1. Define Zod schemas for context, command records, areas, and constraints. Use inferred types.
   Omitted collections default to empty. Reject duplicate area paths and blank names/text.
2. Keep schema validation separate from filesystem checks. Perform containment and existence
   checks in project loading, with stable domain codes and field-specific messages.
3. Add the reserved name check to registry composition. Allow project roots to move across
   machines without putting absolute paths into serialized facts.
4. Add JSON Schema descriptions and a small fixture. Regenerate schema after building core.

Acceptance: old configs stay identical; valid monorepo facts load; empty context is harmless;
invalid paths, missing paths, escaping symlinks, and reserved-name collisions fail explicitly;
command strings with shell syntax stay literal data and cause no execution.

Verification: config/schema/project tests and the common gate.

## R080-02 — Render and manage one canonical context skill

Prerequisite: R080-01. Start with skill serialization, project composition, assets, install
resolution, adapters planning, and manifest ownership tests.

Steps:

1. Add the Markdown template asset and deterministic fact serializer. Sort command keys;
   preserve area/constraint order as authored. Escape/fence data so arbitrary strings cannot
   accidentally break the generated document structure.
2. Contribute the generated skill when context is non-empty. `resolve` lists its identifier;
   explain identifies `project-context` as its origin without inventing a fake pack name.
3. Ensure all config-based consumers load the same generated content. Make `skill show
   agentyx-project-context` work in a configured project and give a readable error without context.
4. Pass the same skill bytes to all adapters. Record ownership/hashes using existing lifecycle
   machinery. Context edits produce updates; removing context proposes removal only with prune.
5. Package the template; verify loading from built artifacts outside the checkout.

Acceptance: two providers install byte-identical context instructions; repeated rendering is
deterministic; edited generated output conflicts; config edits do not overwrite the local edit;
removing context plus prune removes only managed output; no `AGENTS.md` or source file changes.

Verification: core rendering and CLI tests; adapter lifecycle tests; common gate;
`pnpm smoke:pack` including the template and generated skill.

## R080-03 — Offer conservative command suggestions during init

Prerequisite: R080-02. Start with project detector, CLI init/prompts, and onboarding tests.

Steps:

1. Inspect root `package.json` scripts only. Suggest existing `check`, `test`, `build`, and `lint`
   scripts using the unambiguous detected package manager's `run` syntax.
2. Show the suggestions in interactive init and require selection before including them.
   Use an initially empty selection so accepting unrelated defaults does not invent project policy.
3. Non-interactive init does not synthesize context. Users can author the explicit JSON fields.
   If the package manager is ambiguous, omit command suggestions and explain why.
4. Keep areas and constraints manually authored. Do not crawl workspaces, guess package ownership,
   copy existing instruction files, or call an LLM to infer conventions.
5. Document activation limits, source-of-truth editing in `.agentyx.json`, and the full edit/install/
   conflict/prune lifecycle. Add the minor Changeset and packaged scenario.

Acceptance: accepting a real `check` script produces the expected literal command; declining leaves
context absent; an unknown script is never invented; no scripts are run during detection; existing
init behavior still works without context; a monorepo can describe package commands manually.

Verification: detector/init tests, common gate, packaged workflow, interactive acceptance notes.
Release exit: all three tasks pass; a fresh session can discover accurate project guidance through
the installed skill, with actual provider activation left for the runtime trials in 0.10.
