# 0.6 — Finish onboarding and correct misleading diagnostics

Read [the playbook](session-playbook.md). This release line closes the existing onboarding work
before introducing new configuration concepts.

## R060-01 — Validate the pending onboarding release

Prerequisite: inspected baseline. Target release: `0.6.0`.

Start with `packages/cli/src/commands/init.ts`, `commands/install.ts`, `prompts.ts`, their tests,
`packages/adapters/src/detect.ts`, `packages/cli/scripts/pack-smoke.mjs`, and the pending
`.changeset/spotty-agents-onboard.md`.

Steps:

1. Verify the already-implemented target detection, searchable selection, and `init --install`
   against the pending changeset. Do not implement a second onboarding flow.
2. Exercise interactive acceptance manually in a scratch project and scripted acceptance through
   the packaged CLI. Add only missing meaningful coverage or fixes revealed by these checks.
3. Ensure examples distinguish interactive installation from non-interactive config-only init.
   A successful config-only init must identify the remaining install step.
4. Prepare release notes from actual behavior. Preserve the existing minor changeset; do not
   manually bump versions or publish as part of this task.

Acceptance:

- A clean TypeScript project can reach installed skills with explicit packs, target, `--yes`,
  and `--install`, without a second command.
- Scripted init without `--install` writes config only and gives an actionable next command.
- Canceling a prompt does not report success or install a partial selection. Any existing config
  remains untouched; document the exact write boundary if config creation precedes a later prompt.
- A shared `.agents/skills` directory alone is not treated as proof that a specific provider is used.
- An existing user skill with a selected name produces a conflict, not an overwrite.
- Running a packaged binary outside the checkout finds built-in assets.

Verification: common gate; init/install/detection tests; `pnpm smoke:pack`; interactive notes.
Exit: pending onboarding behavior is verified and release preparation is reviewable.

## R061-01 — Correct doctor readiness using the existing report shape

Prerequisite: R060-01. Target release: `0.6.1` bug fix.

Start with `packages/cli/src/commands/doctor.ts`, `packages/cli/test/doctor-command.test.ts`,
and install-plan summary behavior in adapters.

Steps:

1. Reproduce the existing test that reports `healthy` with seven creates and no installed skills.
2. Add warning diagnostics for pending create/update operations and for zero configured targets.
   Use stable codes `installation_pending` and `no_targets_configured`. Include a concrete next step.
3. For an active selected local tool whose executable is absent, add
   `required_tool_missing` as a warning. Do not warn for disabled optional tools.
4. Keep `status` values and exit rules: errors fail normally; warnings fail under `--check`.
   Explain in release notes that CI now catches previously missed incomplete setup.
5. Preserve existing stale/drift/conflict diagnostics. Deduplicate counts for shared target paths.

Acceptance matrix:

| State | Status | Normal exit | `--check` exit |
| --- | --- | --- | --- |
| Valid config, missing installation | warnings | success | 1 |
| Valid config, no targets | warnings | success | 1 |
| Installed, selected tool missing | warnings | success | 1 |
| Installed, optional tool disabled and absent | healthy, absent other issues | success | success |
| Unmanaged destination conflict | errors | 1 | 1 |
| Complete supported installation and available local requirements | healthy | success | success |

Verification: doctor command tests, full gate, built CLI `doctor --check` in scratch projects.
Exit: `healthy` no longer means merely that configuration can resolve.

## R062-01 — Audit and fix demonstrated lifecycle defects

Prerequisite: R061-01. Target: `0.6.2` only if a correction is necessary.

Start with `packages/adapters/src/plan.ts`, `planner.ts`, `executor.ts`, `path.ts`,
`mcp-rendering.ts`, `packages/core/src/config/project.ts`, and adjacent tests.

Steps:

1. Check conflict aggregation covers skill and MCP operations; verify a conflict in one target
   prevents the CLI from applying the other targets.
2. Audit real-path containment for local skill roots and the actual `SKILL.md` read, including
   a file symlink. Audit destination containment on install and deletion.
3. Verify unrelated MCP keys and user edits survive install/prune/uninstall; inspect both JSON
   and TOML adapters. Preserve unknown entries even when their formatting changes legitimately.
4. Verify unchanged install does not rewrite skill/MCP files or byte-identical lock content.
5. Turn each confirmed defect into a focused regression test and fix. If all cases already pass,
   record evidence and skip the patch release. Do not invent a defect from a suspicious code pattern.

Acceptance: unmanaged files survive, edited content conflicts, symlink escapes fail, shared files
retain remaining owners, all target conflicts are reported before writes, no-op install leaves
file modification times unchanged.

Verification: focused core/adapter/CLI tests, common gate, scratch lifecycle and package smoke.
Exit: known ownership defects are closed before adding new managed content or lock semantics.
