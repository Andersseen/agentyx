# 1.0 — Commit to a stable product contract

Prerequisite: all tasks through R100-04, including the human and platform evidence.
Read [the playbook](session-playbook.md).

## R1000-01 — Freeze and document compatibility

Steps:

1. Write a concise compatibility document covering config fields/defaults, manifest formats and
   migration, exported package APIs actually intended for consumers, supported adapters/OS/Node
   versions, exit behavior, domain diagnostic codes, and machine-readable output shapes.
2. Define post-1.0 versioning policy: compatible bug fixes are patches, additive capabilities are
   minors, and incompatible changes to documented config/lock/CLI/API contracts require a major
   release or a documented compatible transition. Keep the existing fixed package release group.
3. Separate human prose from machine contracts. JSON may gain documented optional fields in a
   minor; removing fields, changing their meaning/type, or changing established exit semantics
   incompatibly requires a major. Consumers must tolerate unknown additive fields.
4. Treat default skill-content changes as observable behavior: corrections may be patches,
   new workflow requirements are minors, and incompatible product guarantees need a major.
   Exact CLI/content matching in frozen mode requires a normal reviewed refresh on upgrades.
5. Document unsupported behaviors, local-only guarantees, third-party runtime limits, failed-install
   recovery, and the absence of crash-atomic or concurrent-install guarantees. Remove claims of
   identical agent behavior or guaranteed token savings unless supported by scoped evidence.
6. Check every README example against the built/packed CLI and reference current capabilities.
   Keep future ideas in the roadmap. Ensure source comments do not contradict current MCP support
   or the new lock contract.

Acceptance: a maintainer can tell whether a change is breaking without reading implementation;
an existing 0.5/version-1 project has a tested migration path; consumers know which JSON fields
and public exports are supported; the docs explain how to recover from the known failure modes.

Verification: common gate; documented-command smoke; review of compatibility and migration examples.
Do not generate broad snapshot tests that freeze incidental prose or internal implementation.

## R1000-02 — Complete the release gates and prepare 1.0

Prerequisite: R1000-01.

All of these must have concrete evidence:

| Gate | Required evidence |
| --- | --- |
| Correctness | `pnpm check` passes on the release candidate |
| CLI behavior | Required built-binary success/error checks pass |
| Published artifacts | `pnpm smoke:pack` passes; schemas and Markdown templates are included |
| Platform support | Claimed OS/Node matrix from R100-01 is green |
| Ownership | Shared targets, unmanaged files, edited content, prune and uninstall scenarios pass |
| Failure handling | Stale-plan and partial-failure cases from R100-02 pass |
| Reproducibility | Version-1 migration, frozen restore, mismatch rejection, and lock invariance pass |
| Practical usefulness | R100-03's final evaluation gate passes with sanitized results |
| Real projects | All three pilots complete and existing providers have real discovery evidence |
| Documentation | Current behavior, limits, compatibility, migration, and recovery are documented |
| Release hygiene | No unresolved release blockers; versions/changelogs/dependency ranges are coherent |

Steps:

1. Recheck the release candidate commit, pending Changesets, and fixed-group versions. Prepare
   the 1.0 major Changeset/release PR through the existing workflow; do not edit generated version
   files or release history by hand.
2. Run the full technical gates and link the already-completed external evidence. Repeat runtime
   trials only when changes since those trials invalidate their results.
3. Write release notes around the user outcomes: explainable selection, project facts, reliable
   diagnostics, reversible installation, and locked reproduction. Include upgrade instructions
   and explicit third-party runtime limits.
4. Record a go/no-go decision with blockers and supporting evidence. Publication remains a
   separately authorized action; a prepared release is not a published release.
5. After authorized publication, verify the exact registry version from a clean scratch project,
   run the documented onboarding and frozen workflow, and record the artifact/version. Do not
   claim a registry install was tested if only a local tarball was tested.

Acceptance: all gates are green, release materials are reviewable, and publication status is
accurate. If the practical usefulness gate is still pending, remain pre-1.0 even if the code passes.

## After 1.0

Keep maintenance focused on compatibility fixes, clearer diagnostics, validated instruction
improvements, and defects found in real use. Evaluate any larger addition against three questions:

1. Which observed user problem does it solve?
2. Can it fit the existing configuration/resolution/adapter model without a service or runtime?
3. What test or user evidence will show that it helped?

Additional providers, richer external skill assets, or wider detection can have separate proposals
after 1.0. Their omission is deliberate; they are not unfinished acceptance criteria for this plan.
