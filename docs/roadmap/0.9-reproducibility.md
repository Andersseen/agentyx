# 0.9 — Reproduce a reviewed local environment

Prerequisite: R080-03. Read [the playbook](session-playbook.md).

## Chosen design and limits

Extend `.agentyx.lock.json` to format version 2. Keep two separate concepts inside that file:

- `entries`: ownership of what Agentyx actually wrote, including retained stale files.
- `resolution`: the expected complete project configuration and generated capabilities,
  represented by stable metadata and hashes, or `null` when no complete resolution was recorded.

A resolution snapshot is not a second source of deletion authority. Only ownership entries
authorize edits/deletions. A hash can detect a difference; it cannot recover unavailable content.
Restoration requires the same pinned Agentyx package and the same checked-in local skill sources.

The snapshot records:

| Field | Meaning |
| --- | --- |
| `agentyxVersion` | Exact released CLI package version used for complete project installation |
| `configHash` | Hash of canonical validated config, excluding the editor-only `$schema` field |
| `targets` | Effective selected target IDs, with deterministic ordering |
| `skills` | Effective identifiers, provenance, and hashes of canonical installed skill bytes |
| `mcpServers` | Effective identifiers and hashes of provider-neutral definitions using env references |
| `tools` | Effective identifiers and hashes of declared tool definitions |

Canonicalization sorts object keys and preserves array order unless the schema explicitly defines
set semantics. No timestamps, absolute checkout paths, credentials, environment values, whole
user-owned provider configs, or unrelated unselected skill content enter the snapshot.

The exact CLI version and content hashes deliberately make upgrades require a normal reviewed
installation before frozen mode can pass. Resolve the version at the CLI boundary from packaged
metadata; pass it as data to core. Core must not import CLI. The fixed package group plus hashes
is sufficient; do not introduce a remote catalog or version solver.

User-facing additions:

- `install --frozen`: require a matching version-2 snapshot, then restore missing managed output
  from available sources without changing lock bytes or accepting changed managed content.
- `doctor --locked`: read-only comparison of current inputs with the snapshot; mismatch is an
  error even without `--check`. Other doctor readiness checks still apply.
- `install --migrate-lock`: explicitly validate and upgrade a version-1 lock while doing a normal
  full project installation. Dry-run explains the migration without writing.

Frozen mode is full-project and non-interactive. Reject combining it with manual skill/MCP
selection, `--select`, pack arguments, target overrides, enable overrides, `--force`, `--prune`,
or `--migrate-lock`. Normal installs retain those existing modes where already supported.
Manual or partial-target installation writes ownership but invalidates the full snapshot by setting
`resolution` to `null`; explain that a normal config-based full install is needed to recreate it.

An empty full-project selection may retain a version-2 lock with an empty snapshot. Successful
full uninstall removes the lock when no managed ownership remains. Partial uninstall preserves
remaining ownership and invalidates the snapshot. Normal installs retain stale ownership until
explicit prune; frozen install rejects stale managed entries with an instruction to review and
run a normal prune first. This keeps frozen behavior simple and non-destructive.

Version 1 remains readable for doctor and uninstall. Default install refuses to rewrite it without
`--migrate-lock`. Unknown future versions fail without writes. Do not silently normalize an invalid
manifest or use migration as permission to overwrite edited content.

This contract reproduces Agentyx-managed skill bytes and provider-neutral MCP configuration intent.
It does not pin an executable launched through `npx`, remote MCP software, authorization state,
provider/model versions, or the behavior of an agent.

## R090-01 — Add the version-2 model and deterministic snapshot

Prerequisite: R080-03. Start with core manifest schema/io/errors, config resolution, canonical skill
formatting, and CLI package version access.

Steps:

1. Model version 1 and version 2 explicitly with Zod. Keep ownership access available for both.
   Introduce the nullable resolution snapshot and infer types from schemas.
2. Implement pure deterministic snapshot creation/comparison. Return structured difference
   categories: CLI version, config, targets, skill content, MCP definition, tool definition.
3. Update serialization so it does not drop snapshot fields. Preserve stable ownership ordering.
4. Obtain the package version reliably from the packed CLI and pass it to snapshot construction.
   Do not hardcode the next release version in source.

Acceptance: same effective inputs produce identical bytes across checkout paths; changing selected
local skill content changes its hash; changing an unselected skill does not; environment values
never change the snapshot; `$schema` changes do not invalidate it; unknown versions fail.

Verification: manifest/snapshot unit tests and common gate. Add packed-version verification in the
smoke script because unit aliases do not test packaged metadata lookup.

## R090-02 — Record snapshots and implement explicit migration

Prerequisite: R090-01. Start with install orchestration, adapter executor's `nextManifest`, manifest
loading, uninstall behavior, and their tests.

Steps:

1. Have the full config-based install compute a candidate snapshot before applying plans and
   persist it through the existing executor only after successful complete application.
2. Preserve retained stale ownership separately from the desired snapshot. Manual/partial operations
   invalidate the snapshot; they must not falsely record a complete environment.
3. Implement version-1 migration only with the explicit flag. Validate old ownership and current
   conflicts first; do not claim previously unmanaged files because their names look familiar.
4. Implement the empty-install and uninstall rules from the design contract. Keep repeated
   unchanged installs from rewriting the lock.
5. Explain migration and snapshot invalidation in text/JSON install reports without secret data.

Acceptance: normal full install records the snapshot; no-op install preserves bytes/mtime; manual
install sets snapshot to null; target-limited uninstall preserves other owners; failed migration
does not claim a new snapshot; version-1 edited files still conflict; dry-run does not migrate.

Verification: manifest/executor/install/uninstall tests, common gate, scratch migration lifecycle.

## R090-03 — Add locked comparison and frozen installation

Prerequisite: R090-02. Start with doctor/install command parsing and orchestration, snapshot
comparison, adapter plans, and domain errors.

Steps:

1. Implement `doctor --locked` with structured diagnostics for absent lock, legacy lock,
   absent complete snapshot, and mismatch. Ordinary doctor remains usable on legacy locks.
2. Validate frozen flag combinations before any prompting or writes. Compare all snapshot inputs
   before planning writes; reject differences with specific next steps.
3. Allow reconstruction of a missing managed skill from matching available source content.
   Keep existing ownership/conflict checks for present destinations. Reject stale ownership.
4. Ensure frozen mode never rewrites the lock. An MCP merge that would change recorded ownership
   or hashes fails rather than silently accepting a new shared-file state.
5. Distinguish a matching input snapshot from installed readiness: `doctor --locked` can have a
   matching snapshot while ordinary readiness reports missing output. Document `--check` for CI.

Acceptance matrix:

| Situation | Frozen outcome |
| --- | --- |
| Matching sources, version, config, installation | Success; no writes |
| Matching snapshot, one managed skill absent | Restore that skill; lock unchanged |
| Changed config or selected skill source | Fail before writes |
| Different Agentyx version | Fail with reviewed normal-install guidance |
| Missing, legacy, or null-snapshot lock | Fail with specific recovery step |
| Manually edited managed file | Conflict; no overwrite |
| Stale ownership outside desired selection | Fail; request reviewed normal prune |
| Unrelated provider edit requiring a different MCP merge/hash | Fail; normal install must review it |

Verification: command-function tests, scratch tests asserting byte/mtime invariance, common gate,
built CLI success/error cases. Do not add network access to restore unavailable sources.
