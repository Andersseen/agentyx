# 0.10 — Validate reliability and practical usefulness

Prerequisite: R090-04. Read [the playbook](session-playbook.md).
This milestone spends effort on evidence and correction, not catalog growth.

## Evidence boundaries

Keep deterministic software checks separate from trials of agent behavior. Both matter, but one
cannot stand in for the other. Trials are maintainer-operated and optional during normal local
development; Agentyx does not gain an agent runner, credentials, billing, or telemetry.

Use `evals/` for fixture/task definitions and `evals/results/` for sanitized reports. Do not commit
provider tokens, private repositories, unreviewed raw transcripts, or personal information.
Manual real-agent trials require a human with appropriate provider access. If unavailable, complete
the rest of the work and leave this release gate pending rather than inventing results.

## R100-01 — Establish a concrete compatibility matrix

Prerequisite: R090-04. Start with adapter references/capabilities, rendering tests, package smoke,
`.github/workflows/ci.yml`, and the current supported Node engines.

Steps:

1. Record a dated matrix for the three existing providers: supported project skill location,
   MCP config path/format, supported transports, shared-directory behavior, and official sources.
   Check official provider documentation at implementation time; do not rely on this roadmap
   for current third-party formats or claim global settings are supported.
2. Add narrow adapter contract fixtures for canonical skill equality, MCP env references,
   unsupported transports, and preservation of unrelated user keys.
3. Run the full existing Linux checks on Node 22 and 24. Add installation/artifact smoke coverage
   on macOS and Windows using Node 22. Reassess supported Node lines at release time and document
   any engine-policy change explicitly.
4. Fix shell/path assumptions exposed by real platform runs. Keep CLI unit tests process-free;
   use standalone smoke scripts for executing packed binaries.

Acceptance: all claimed OS/provider-format combinations have evidence; unsupported combinations
are labeled; copied canonical skills are byte-identical across adapters; package smoke passes
outside the workspace on each claimed OS. Do not equate config rendering tests with real provider
activation, which is validated in R100-03/R100-04.

Verification: common gate; OS CI results; package smoke; dated compatibility document in `docs/`.

## R100-02 — Harden stale-plan and partial-failure behavior

Prerequisite: R090-04. Start with planner operation data, executor, domain errors, and filesystem tests.

Steps:

1. Capture observed destination state during planning and revalidate all planned mutations before
   applying any of them. Check each destination again immediately before its operation. Detect
   a file edited or newly created after planning and fail without overwriting that new content.
2. Keep the existing explicit force decision bounded to the state the user selected. `--force`
   does not waive containment or permit silently accepting a different state after planning.
3. Add deterministic fault-injection tests for an I/O failure after one successful write and for
   a lock-write failure. Use existing testing facilities; do not introduce a filesystem abstraction
   framework solely for injection.
4. Return a stable domain error for incomplete application with sanitized completed/pending paths.
   Do not print success or persist a complete resolution snapshot after partial application.
5. Document conservative recovery using doctor, the prior lock, and reviewed source content.
   An unrecorded newly written file remains a conflict on the next run; do not auto-adopt it based
   solely on its name or content. Explain the exact manual recovery step without recommending
   blanket deletion or blanket force.

Acceptance: an edit between planning and application survives; a newly created destination is not
overwritten; ordinary detected conflicts stop before writes; mid-run I/O failure yields nonzero
exit and specific recovery guidance; no complete snapshot claims success after partial failure;
unknown files are never automatically adopted or deleted during recovery.

Limits to state explicitly: this is conservative failure handling, not an atomic multi-file
transaction. A process crash or concurrent filesystem mutation can leave partial state. Concurrent
installers are unsupported. Do not add a daemon, transaction journal, backup tree, or automatic
rollback subsystem in this milestone. If real-project evidence makes crash-atomic recovery a 1.0
requirement, reopen the design as a separately scoped decision instead of claiming these tests
provide it.

Verification: planner/executor and CLI error tests, common gate, scratch interrupted-install exercise.

## R100-03 — Replace evaluation claims with measured behavior evidence

Prerequisite: R090-04. Start with `evals/skill-behavior.json`, `scripts/evaluate-skills.mjs`, and
selected built-in skill files.

Steps:

1. Keep `pnpm eval:skills` as a fast deterministic validation command. Rename its description/output
   where necessary to make clear it validates the evaluation suite, not agent quality.
2. Define six small fixture tasks with an initial commit/state, exact prompt, objective acceptance
   checks, and a simple human rubric: a reproducible bug, an API change, a safe refactor, project
   command discovery, a misleading/non-applicable skill situation, and an existing-instruction
   coexistence case. At least one task must test whether a skill stays out of an irrelevant task.
3. Define a baseline that preserves the repository's normal tooling and instructions but omits
   Agentyx-managed additions. Compare against the same repository plus a documented minimal
   Agentyx configuration. Keep provider/model/version/settings and starting state matched.
4. Run each task three times per condition in each of two available supported providers: 72 total
   runs. Reset fixtures and start fresh sessions; alternate condition order. Do not claim provider
   coverage for any provider not actually tested.
5. Record task success, regressions, human interventions after the fixed initial prompt, and
   whether the relevant instruction was visibly used. Record time/tokens only where consistently
   observable and comparable. Document ambiguous activation as unknown.
6. Report counts, per-task outcomes, and failures; do not substitute keyword presence in the
   answer for passing the task's checks. Refine or remove ineffective default instructions using
   evidence, then rerun affected cases with both conditions.

Internal release gate: with the final instruction set, aggregate correctness in each tested
provider must be no worse than its baseline; no critical destructive or secret-disclosure behavior
introduced by the instructions is acceptable. At least two task categories must show a documented
benefit in correctness or reduced human intervention without a correctness loss. Treat these as
practical internal acceptance thresholds, not proof of statistical superiority or universal gains.

If the gate fails: reduce default scope, correct instructions, and repeat affected comparisons.
Do not add more skills to obscure negative results or relax the gate silently. Claims about
improvement must name the tested tasks/providers and sample size.

Verification: suite validation, fixture checks, sanitized result reports, common gate for any
instruction/code changes, and package smoke if assets changed. Human trial completion is a
separate prerequisite; a passing `pnpm check` does not complete this task.

## R100-04 — Run three real-project pilots and freeze scope

Prerequisite: R100-01, R100-02, and R100-03.

Use three repositories: a small TypeScript project, an Angular application, and a TypeScript
monorepo. At least one pilot should be operated by someone other than the feature implementer.
Use the third supported provider for at least one installation/activation trial if it was absent
from the comparative evaluation. Obtain access through the person running the pilot; do not send
messages or modify third-party repositories without session authorization.

For each pilot, record:

1. Fresh setup: init, dry-run, install, doctor, and an explanation of one selected capability.
2. Adjustment: exclude a capability and remove managed output using reviewed prune.
3. Project fit: use a real command from context and verify the agent finds it in a fresh session.
4. Reproduction: restore a missing managed skill with a pinned CLI and frozen lock.
5. Maintenance: edit managed content, observe the conflict, and recover deliberately.
6. Removal: uninstall and check that existing skills and unrelated MCP configuration survive.

Record completion, help required, confusing output, and actual failures. All six workflows must
complete in all three repositories with no destructive changes. Every supported provider must
have at least one real skill-discovery trial and an explicit record of which MCP transport was
actually tried; do not imply live coverage for untried servers.

Classify findings as release blockers, patch fixes, or post-1.0 requests. Blockers include loss of
user content, false success, unrecoverable documented workflow, leaking secrets, and a claimed
provider integration that cannot discover the installed skill. Fix and retest affected workflows.

Update current product docs and website copy to match evidence. Follow the website skill if
editing `apps/web`; avoid an unrelated visual redesign. Prepare a `0.10.0` minor Changeset for
the actual new contract/reliability behavior, not for the mere existence of reports. Later
corrections are patches. Freeze new capabilities when the pilots pass.

Verification: common gate for changes, pilot evidence, compatibility matrix, evaluation gate,
and package smoke. Release exit: no unresolved blockers and a bounded stabilization list for 1.0.
