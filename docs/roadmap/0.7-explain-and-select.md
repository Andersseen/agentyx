# 0.7 — Explain selection and report local readiness

Prerequisite: R061-01 and any confirmed safety fixes from R062-01.
Read [the playbook](session-playbook.md).

## Chosen design

Add `resolve --explain` and optional typed exclusions in `.agentyx.json`:

```json
{
  "packs": ["technical", "testing"],
  "exclude": {
    "skills": ["api-design"],
    "mcpServers": ["playwright"],
    "tools": []
  },
  "targets": ["claude"]
}
```

Examples must be checked against the registry before publication. `exclude` is optional and each
array defaults to empty. It accepts capabilities declared by selected packs, including local packs;
unknown or unselected names fail. This catches typos and stale exclusions. A capability explicitly
enabled and excluded in the same configuration is an error. Match by kind and name, not name alone.

Resolution order is: validate configuration, collect pack contributions, validate enable/exclude,
apply activation and exclusions, deduplicate effective capabilities, then plan installation.
Preserve first-contribution ordering. Exclusion never mutates a pack or automatically prunes files.

Do not add profiles, inherited packs, per-provider skill bodies, an interactive configuration editor,
or a general policy language. Existing manual install selection remains a separate path: reject
mixing manual skills/MCP selection with pack composition or exclusion overrides.

## R070-01 — Add resolution provenance and explain output

Prerequisite: R061-01. Start with core config/pack/skill/MCP/tool resolvers and CLI `resolve.ts`.

Steps:

1. Define a Zod-backed explanation entry with `kind`, `name`, `contributedBy` pack names,
   `active`, and `reason` (`default`, `explicitly-enabled`, `optional-disabled`, `excluded`).
2. Generate provenance in core from the same data used for effective resolution. All contributing
   packs appear once, in configuration order; do not build a second independent resolver in CLI.
3. Expose explanation through `resolve --explain`. Normal text and existing `resolve --json`
   retain their current shapes. `--explain --json` returns `{ resolution, explanation }`.
4. Render identifiers and selection reasons, never full skill bodies or environment values.
   Extend this entry in 0.8 for the explicit project-context origin.

Acceptance: two packs contributing one capability produce one effective capability with both
origins; a disabled optional MCP explains why it is absent; local pack origins work; explicit
pack arguments keep their existing config-bypass behavior; JSON stdout contains only JSON.

Verification: resolver and resolve-command tests; common gate and built explain smoke check.

## R070-02 — Add typed exclusions throughout composition

Prerequisite: R070-01. Start with `config/schema.ts`, `config/resolver.ts`, config errors,
CLI install/resolve integration, generated schema, and associated tests.

Steps:

1. Add the optional `exclude` object using existing capability name schemas and inferred types.
2. Implement the chosen order and typed validation. Use stable errors
   `unknown_excluded_capability` and `contradictory_capability_selection`.
3. Make every config-based command consume the same effective resolution, including doctor,
   install, and explain. Keep excluded entries visible in explanation.
4. Do not add exclusion flags in this release. Config exclusions apply only when config is used;
   `resolve <packs...>` remains an explicit independent inspection.
5. Document that existing installed files remain until `install --prune` and that removing a pack
   may require removing its exclusions too.

Acceptance: exclude a default skill; exclude an optional MCP; reject unknown or wrong-kind names;
reject enabled-and-excluded optional capability; deduplicate repeated exclusions; exclude a local
pack skill; old configs resolve identically; prune preserves a manually edited excluded skill.

Verification: schema regeneration after core build; resolver/CLI/planner tests; common gate;
scratch install, edit config, dry-run prune, real prune.

## R070-03 — Make local prerequisite diagnostics precise

Prerequisite: R070-02. Start with doctor, MCP definitions, adapter capabilities, and plan reports.

Steps:

1. Add an additive `readiness` section to doctor JSON with independent states for configuration,
   installation, and local prerequisites. Use `ready`, `not-ready`, or `unknown`; document
   conditions rather than collapsing unperformed checks into success.
2. Inspect executable availability for active tools and active stdio MCP commands. Inspect only
   names of referenced environment variables in active MCP `env` and HTTP `headers` mappings.
   Unset or empty values are missing; do not read `.env` files or print values.
3. Report unsupported selected MCP transports/scopes from adapters as errors with target and
   server identifiers. Disabled capabilities produce no missing-requirement warnings.
4. Add stable warning codes `mcp_command_missing` and `mcp_environment_missing`, and error code
   `mcp_unsupported`. Carry structured identifiers on diagnostics; do not make callers parse prose.
5. Label MCP execution/connectivity/authentication as unverified. Presence of `npx`, a URL, or a
   provider config does not prove a server starts or a remote session is authorized.

Acceptance: absent launcher warns; available launcher cannot imply installed npm package;
missing referenced variable warns without exposing values; disabled MCP is quiet; unsupported
transport errors; malformed provider config yields a readable diagnostic instead of an unhandled
stack trace; doctor performs no network requests, subprocess execution, or writes.

Verification: isolated environment/PATH tests that restore process state; adapter/doctor tests;
common gate; inspect JSON using dummy secret values and assert those values never appear.
